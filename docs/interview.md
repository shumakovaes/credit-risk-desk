# Для резюме и собеседования

## Два пункта в резюме

- Разработал учебный сервис кредитной аналитики на Python, PostgreSQL, FastAPI и Streamlit: импорт и проверки данных, портфель, карточка клиента, калькулятор, бизнес-правила, журнал заявок и экспорт отчётов. Обработал 1,06 млн операций Berka; подготовил Docker Compose и автоматические тесты.
- Построил SQL-витрину исторических признаков и Logistic Regression для исходов завершённых розничных кредитов; разделил обучение, выбор порога и тестирование, сравнил с Dummy baseline. На отложенной выборке из 47 кредитов получил ROC-AUC 0,687, документировал ограничения и вклад признаков в отдельную оценку.

Используйте эти формулировки после самостоятельного разбора кода и воспроизведения запуска. Не приписывайте проекту банковское внедрение, корпоративные данные или измеренное ускорение реального бизнеса.

## Что стоит уметь объяснить

**Почему проект подходит вакансии?** Он демонстрирует работу с данными, SQL, API, пользовательским процессом, правилами и проверяемым продуктом. Он не демонстрирует опыт структурирования корпоративных сделок. Агентная часть относится к отдельному второму проекту.

**Почему A/B, а не A/C против B/D?** A/B имеют завершённый исход договора. C/D — текущие состояния; хороший текущий статус не гарантирует успешного окончания.

**Где самая вероятная утечка?** В операциях после выдачи, платежах по уже выданному кредиту и итоговом статусе. Окно SQL ограничено строго до дня выдачи, статус нужен только для target. Порядка операций внутри дня нет.

**Почему random split?** Это ограниченный ретроспективный baseline на 234 завершённых кредитах. Нет надёжной даты появления исхода, поэтому не заявлен временной backtest. Счета разделены, но это не доказывает качество на будущем потоке.

**Почему низкий порог около 10%?** Он минимизирует условную стоимость пропусков и ложных сигналов на validation при соотношении 5:1. Вероятность не равна решению, стоимость не равна реальным денежным потерям.

**Что означает AUC 0,687?** Оценку ранжирования в данном тесте. При шести проблемных кредитах метрика неустойчива; нельзя обещать тот же результат на других данных. Brier близок к простому baseline.

**Чем правила отличаются от ML?** Правила проверяют явно заданные ограничения. Модель оценивает статистический риск. Оба результата сохраняются; нарушение правила не объясняется «так решила модель».

**Почему поступления не равны доходу?** В кредитовых операциях есть переводы и другие поступления. Для ML это прокси денежного потока; правило нагрузки использует отдельно заявленный доход.

**Как обеспечивается одинаковый расчёт при обучении и работе API?** Оба пути вызывают одну PostgreSQL-функцию. Pipeline сохраняет обученные медианы и масштабирование. Есть интеграционный тест на совпадение признаков.

**Что произойдёт при повторном импорте?** Приложение откажется менять уже заполненную базу. Инициализация сериализована, запись атомарна, для другого набора нужна другая БД.

**Что нужно для настоящего банковского использования?** Другая постановка задачи и данные, подтверждённые лимиты и доходы, роли и аудит, качество и доступность данных по времени, контроль дрейфа и ошибок, мониторинг, согласование политики принятия решений. Текущая версия — локальный учебный продукт.
